## 2. Phase-by-Phase Technical Remediation

### Phase 1: Fix T-01 — Critical Heuristic Aggregation Defect

#### Defect Root Cause
In `forecasting/service.py` (`forecast_weight_heuristic`) and `forecasting/management/commands/record_shadow_forecast.py` (`compute_heuristic_points_for_origin`), daily waste totals were populated using the following dictionary comprehension:
```python
# DEFECTIVE CODE:
by_day = {
    row['date']: float(row['kg'] or 0.0)
    for row in qs.values('date').annotate(kg=WEIGHT_EXPR)
}
```
Because `WEIGHT_EXPR` was an individual delivery row expression without a grouping `Sum()`, querying `.values('date').annotate(kg=WEIGHT_EXPR)` returned one row per delivery. The Python dictionary assignment `by_day[row['date']] = ...` repeatedly overwrote the key for that date, retaining only the weight of the last delivery executed on that date and discarding all previous deliveries! In Claude's test scenario of three deliveries of 4,000 kg, 6,000 kg, and 5,000 kg, this resulted in an erroneous daily total of 4,000 kg or 5,000 kg instead of the correct 15,000 kg sum.

#### Exact Remediation
1. **Canonical Aggregation Implementation (`forecasting/aggregation.py`):**
   - Refactored `build_daily_aggregation(start_date, end_date, barangay_id, fill_zeros=True, include_synthetic=False)` as the single authoritative aggregation pipeline across the entire repository.
   - For city-wide aggregations (`barangay_id=None`), all deliveries on each date are summed across all trips:
     $$\text{Daily Total} = \sum_{i \in \text{deliveries}(t)} \text{weight}_i$$
   - For barangay-specific aggregations (`barangay_id=B`), deliveries dedicated to barangay $B$ receive 100% of their net weight. For shared routes serving $N$ barangays ($N > 1$), the net weight is allocated proportionally:
     $$\text{Barangay Allocation} = \sum_{i \in \text{shared}(t, B)} \frac{\text{weight}_i}{N_i}$$
   - Added distinct trip resolution on ManyToMany joins to prevent double-counting.
   - Added weight-source provenance tracking (`weighbridge`, `manual_ticket`, `driver_estimate`).
2. **Production Service Integration (`forecasting/service.py`):**
   - Replaced the defective dictionary comprehension in `forecast_weight_heuristic` with `build_daily_aggregation(start_date=lookback_start, end_date=origin_date, barangay_id=barangay_id, fill_zeros=True, include_synthetic=False)`.
   - The historical daily series passed to the seasonal heuristic now correctly reflects the true sum of all deliveries on each day.
3. **Shadow Evaluation Integration (`forecasting/management/commands/record_shadow_forecast.py`):**
   - Replaced dictionary comprehension in `compute_heuristic_points_for_origin` with `build_daily_aggregation`.
4. **Mandatory Regression Verification:**
   - Regression test `test_36_multi_delivery_same_date_aggregation` creates three deliveries of 4,000 kg, 6,000 kg, and 5,000 kg on the same date. It verifies that `build_daily_aggregation` returns exactly 15,000 kg, `forecast_weight_heuristic` generates baseline predictions conditioned on the 15,000 kg daily sum, and `GET /api/analytics/live/` serves the corrected daily aggregation.
   - Regression test `test_37_shared_route_proportional_allocation` verifies that a 12,000 kg delivery shared between 3 barangays correctly allocates 4,000 kg to each barangay while preserving the unfragmented 12,000 kg city-wide total without double counting.

### Phase 2: Fix T-02 — City Population Train/Serve Alignment

#### Defect Root Cause
In prior iterations, `train_waste_forecast.py` calculated city population as the sum of all barangay populations in the database ($\sum \text{pop}_b \approx 270,000$), while `service.py` and `record_shadow_forecast.py` passed `0.0` or an ad-hoc fallback for city-level inferences. This created a severe train/serve feature skew for the city-wide feature vector.

#### Exact Remediation
1. **Canonical City Population Function (`forecasting/features.py`):**
   - Created `get_canonical_city_population()`:
     ```python
     def get_canonical_city_population():
         from accounts.models import Barangay
         agg = Barangay.objects.filter(is_active=True).aggregate(total=models.Sum('population'))
         total = agg.get('total')
         if total and total > 0:
             return float(total)
         return 270000.0  # Official Lucena City PSA Census baseline
     ```
   - Created `get_series_population(barangay_obj=None)` to enforce identical population retrieval semantics across all callers.
2. **Serving & Training Alignment:**
   - Updated `train_waste_forecast.py` to extract city population via `get_canonical_city_population()`.
   - Updated `forecasting/service.py` (`get_waste_forecast`) to compute city population via `get_canonical_city_population()` instead of `0.0`.
   - Updated `record_shadow_forecast.py` to use `get_canonical_city_population()`.
3. **Deterministic Verification:**
   - Added `test_38_city_population_train_serve_alignment` which extracts the feature matrix built during training and compares it directly against the feature vector produced during inference for the identical city-wide series. Asserts that `pop_feature_train == pop_feature_serve == get_canonical_city_population()`.

### Phase 3: Fix N-08/T-05 — Safe Schedule Behavior

#### Defect Root Cause
The legacy schedule helper caught database exceptions and defaulted to `return False`. This caused any transient database failure or query issue to be misinterpreted as a confirmed non-collection day, erroneously forcing Sunday predictions to 0 kg. Furthermore, substring matching on day names (`"sun" in schedule.day`) led to false positives, and inactive trucks or cancelled routes were not filtered.

#### Exact Remediation
1. **Schedule Status Enumeration (`forecasting/features.py`):**
   - Defined `ScheduleStatus` with three explicit states:
     - `SCHEDULED`: Confirmed active truck collection scheduled.
     - `CONFIRMED_NON_COLLECTION`: Active schedule exists explicitly designating no collection.
     - `UNKNOWN`: No schedule record exists, date is in the historical past, schedule state is inactive/cancelled, or a database exception occurred.
2. **Safe Schedule Query Logic (`check_collection_schedule`):**
   - Uses exact regex word boundaries `r'\b(sun|sunday)\b'` against normalized day strings.
   - Filters out `status__in=['cancelled', 'inactive']`.
   - Requires assigned truck to have `is_active=True`.
   - Guards historical dates: schedule queries for dates in the past return `ScheduleStatus.UNKNOWN` to prevent using current operational schedules as an unverified proxy for historical operations.
   - Catches database errors and returns `ScheduleStatus.UNKNOWN` rather than `False`.
3. **Forecasting Invariance:**
   - In `forecasting/models.py` (`predict_7_days`) and `forecasting/service.py` (`forecast_weight_heuristic`), predictions and prediction intervals are clamped to 0 kg if and only if `status == ScheduleStatus.CONFIRMED_NON_COLLECTION`.
   - When status is `ScheduleStatus.UNKNOWN`, the normal historical baseline seasonal prediction and non-zero uncertainty intervals are fully preserved.
4. **Philippine Movable Holidays:**
   - Added Meeus/Jones/Butcher algorithm to dynamically compute Easter Sunday, Maundy Thursday, Good Friday, and Black Saturday for any calendar year, eliminating static holiday lookup errors.

### Phase 4: Shadow Evaluation Architecture and Data Integrity

#### Defect Root Cause
Previous shadow evaluation attempts suffered from circular governance (requiring candidate models to pass production promotion gates before shadow evaluation could record their predictions), lacked database-level uniqueness for city-wide records (due to SQL `NULL != NULL` semantics on nullable foreign keys), and overwrote historical records instead of preserving immutability.

#### Exact Remediation
1. **Schema Refactoring (`analytics/models.py`):**
   - Added non-null `series_id` field: `'city'` for city-wide predictions, `'brgy_<id>'` for barangay-specific predictions.
   - Replaced composite unique constraint on `(origin_date, target_date, horizon_step, barangay, model_version)` with `UniqueConstraint(fields=['origin_date', 'target_date', 'horizon_step', 'series_id', 'model_version'])`. This guarantees absolute uniqueness at the database engine level for city-wide records.
   - Added `is_backfill` boolean flag to distinguish forward-recorded operational evaluation from retrospective backfills.
   - Added `actual_data_status` field (`in_grace_period`, `confirmed_actual`, `missing_unrecorded`).
   - Made `expected_kg` nullable to permit recording heuristic-only predictions when no candidate Ridge model exists.
   - Added database-level immutability enforcement in `save()`: attempts to mutate existing records raise `IntegrityError` unless explicit supersession flags are passed.
   - Created and applied migrations `analytics.0004` and `analytics.0005`.
2. **Candidate Artifact Resolution (`forecasting/service.py`):**
   - Added `load_candidate_forecaster()`. This loader inspects `candidate_manifest.json` and loads validated candidate artifacts into an isolated evaluation singleton without altering `active_manifest.json` or production serving state.
   - Added artifact path and version string to cache keys, preventing stale model serving.
3. **Operational Shadow Command (`record_shadow_forecast.py`):**
   - Evaluates whether an unpromoted candidate model exists. If present and cryptographically validated, it records both candidate Ridge predictions and baseline heuristic predictions.
   - If no candidate model exists, it logs the condition and records heuristic-only shadow baseline predictions.
   - Enforces a 2-day grace period (`GRACE_PERIOD_DAYS = 2`) for late dumpsite log entries before classifying missing dates as `missing_unrecorded`.
   - Backfills actuals exclusively from validated genuine delivery records using `build_daily_aggregation`.
   - Separates city and barangay metrics in all evaluation logs.

### Phase 5 & 6: Promotion Gate & Artifact Governance

#### Defect Root Cause
The previous promotion gate compared Ridge on a small test fold against an ad-hoc heuristic calculated on a different dataset, used arbitrary hardcoded fallback metrics (e.g. 500.0 kg MAE), pooled city-wide and barangay errors into a single unweighted metric, and lacked pre-activation governance checks.

#### Exact Remediation
1. **Synchronized Cross-Validation (`train_waste_forecast.py`):**
   - Cross-validation now evaluates Ridge and the canonical `forecast_weight_heuristic` on identical test origin dates, predicting identical horizons $h=1..7$, and comparing against identical genuine actuals.
   - Separated evaluation reporting into City-Wide MAE/WAPE and Barangay-Pooled MAE/WAPE.
   - Eliminated all hardcoded metric fallbacks.
   - Prohibits production promotion by default: writes to `candidate_manifest.json` for shadow evaluation.
2. **Artifact Governance and Integrity:**
   - Artifacts require `synthetic_records` to be an integer equal to 0.
   - SHA-256 checksum verification is enforced prior to loading.
   - Metadata stores exact scikit-learn version, Python version, training cutoff, and feature column list.
3. **Pre-Activation Rollback Governance (`rollback_forecast_model.py`):**
   - Before atomically updating `active_manifest.json`, `rollback_forecast_model` loads the target artifact, validates its SHA-256 digest, checks feature schema compatibility, and asserts `synthetic_records == 0`. Any corrupted or synthetic artifact is immediately rejected prior to activation.
